# Benchmarks

These benchmarks measure native execution of polynomial queries, initial extraction, rank comparison, reduction checks, list prefix replacement, standard basic sets, and specified-variable pseudo-division on sparse integer polynomials, plus general pseudo-division by a nonzero rational constant and successive remainders over an ordered rational divisor list.

The benchmark package depends only on `packages/computable` and benchmark tooling.

## Cross-system polynomial multiplication

The optional runner needs Python 3.11+ (standard library only). Maple and
Mathematica are installed and licensed separately by the user. On Linux/macOS,
the runner defaults to `maple`, `wolframscript` and `python3` on PATH. Configure a different
installation once:

```bash
cp bench/config.example.toml bench/config.local.toml
```

Edit `executable` and, if needed, `args` in that file; Git ignores it. Paths with
spaces work without shell quoting inside the TOML string. Relative executable
paths resolve against the configuration file's directory. A standalone
`WolframKernel` can use `args = ["-script"]` instead of wolframscript's `-file`.
Resolution order is `MAPLE_BIN` / `MATHEMATICA_BIN` / `SYMPY_PYTHON`, local configuration, then
the default executable name on PATH. Environment overrides change the executable,
while configured arguments still apply.

```bash
./bench/run.sh run --backend lean
./bench/run.sh run --backend maple
./bench/run.sh run --backend mathematica
./bench/run.sh run --backend sympy
```

For SymPy, create a Python environment and install the pinned dependency:

```bash
uv venv bench/.venv
uv pip install --python bench/.venv/bin/python -r bench/cas/requirements.txt
```

Then set `[sympy].executable = ".venv/bin/python"` in the local config.
SymPy uses `Poly` over `QQ`; its version and coefficient implementation
(`ground_types`) are recorded. The other backends use native Hex multiplication,
Maple `expand`, and Mathematica `Expand`, respectively.

The default `smoke` case is `(x + 1/2)(y - 2/3)` from
[the shared fixture](cas/cases/multiply.json). For meaningful computation timings,
use a larger case and compare all four backends in sequence:

```bash
./bench/run.sh run --backend all --case dense-16 --batch-size 64 --trials 5 --timeout 120
```

`dense-8`, `dense-16` and `dense-32` multiply polynomials with 64, 256 and 1024
terms each. Both variables have exponents from 0 to size-1. Coefficients are
small deterministic rationals; expected products are generated by independent
convolution using Python's exact `Fraction` arithmetic. Arbitrary two-variable
fixtures can still be passed using `--case FILE`.

Each backend warms up once, then prepares distinct operands `q + k` outside the
timer and multiplies `p * (q + k)` in a timed batch (default 16 calls, 3 trials).
Offsets are distinct across all trials, avoiding repeated identical expressions
being served from a symbolic cache. Mathematica also clears its system cache
before each batch. Each result is retained until the timer stops, then serialized
and checked exactly against `expected + k*p`. Timings include the loop and result
storage/allocation, exclude preparation, startup, serialization and verification.
These are multiplication benchmarks, not characteristic-set or pseudo-division
comparisons. Lean and SymPy run in the configured Linux environment, while the
local CAS configuration may invoke Windows executables through WSL.
The clocks are `IO.monoNanosNow`, Maple
[`time[real]`](https://www.maplesoft.com/support/help/maple/view.aspx?path=time),
Mathematica [`AbsoluteTiming`](https://reference.wolfram.com/language/ref/AbsoluteTiming.html),
and Python `perf_counter`, respectively. Small batches can still be dominated
by clock granularity or interpreter/loop overhead; timings apply to the chosen
case and representations, not all algorithms in each system.

The CAS and SymPy backends do not build or launch Lean. Without `--backend`, commands
continue to use the original lean-bench interface below.

Results go to a fresh directory under `bench/.lake/cas-results/`, printed on
completion. Each directory contains `result.json`, canonical `input.json`, and
raw stdout/stderr logs; CAS runs also retain the generated script, and Lean runs
retain `build.log`. `process_seconds` includes process startup and serialization,
excludes Lean compilation, and is diagnostic rather than an algorithm benchmark.
`computation` records per-call batch timings, their median/min/max, and a
`below_resolution` flag when any batch lasted less than 10 ms. Increase
`--batch-size` when flagged; do not interpret a zero time as an infinite speedup.
`--backend all` additionally writes a `summary.json` with all backend results,
and returns nonzero if any backend fails.
An error or result mismatch returns a nonzero exit code. The default process
timeout is 30 seconds, including startup; timed-out wrappers and children are killed.

Use `--config FILE`, `--output-dir DIR`, `--timeout SECONDS` or `--case FILE` to
override defaults. Explicit relative option paths resolve against the caller's
working directory; default paths are independent of it. An output directory
provided explicitly is reused and its artifacts overwritten.

Case JSON has `id`, `variables: ["x", "y"]`, and `lhs`, `rhs`, `expected` term
arrays. Each term contains two nonnegative integer `powers` and decimal string
`num`/`den` fields, with positive denominator. Result JSON uses schema version 1,
records backend/version/case/status, and includes the canonical polynomial on
successful execution. Canonicalization combines equal monomials, removes zeros,
reduces rational coefficients and sorts exponent vectors lexicographically.
The adapters emit one `CSBENCH_VERSION:` line and one `CSBENCH_RESULT:` JSON line
whose object contains a `terms` array in that same term format, plus `samples`
with elapsed `seconds` and an array of result term arrays (`outputs`) per batch.

Infrastructure tests use fake executables to exercise configuration, argument
passing, rational result comparison and failures, without requiring either CAS:

```bash
python3 -m unittest discover -s bench/cas -p 'test_*.py'
```

The infrastructure tests use simulated programs; actual backend runs independently
validate all products, including every item of every timed batch.

## Lean microbenchmarks

### Experimental Basic.lean variants

Compare the frozen original definitions and experimental alternatives against the
production `mainVar` and `mainDegree`, compiled to their fast implementations
through verified `csimp` equalities:

```bash
LEAN_NUM_THREADS=2 ./bench/run.sh basic-variants bench/.lake/basic-variants.json
LEAN_NUM_THREADS=2 ./bench/run.sh basic-variants --verify
```

[BasicVariants.lean](CharacteristicSetBench/BasicVariants.lean) compares:

- `var.original`: original definition (`degrees`, variable support, maximum).
- `var.internal`: production `mainVar`, descending through coordinates above the
  running main variable. Its proof-facing equation is `CharacteristicSet.Computable.mainVar_def`;
  `mainVar_eq_internal` selects the native `mainVarInternal` implementation.
- `degree.original`: original definition (main variable, then `degreeOf`).
- `degree.reuse`: compute `degrees` once and read the selected coordinate.
- `degree.two-pass`: `var.internal` followed by `degreeOf`.
- `degree.internal`: production `mainDegree`, maintaining the main variable and its
  maximum exponent in one term fold. Its proof-facing equation is
  `CharacteristicSet.Computable.mainDegree_def`; `mainDegree_eq_internal` selects the
  native `mainDegreeInternal` implementation.

The original baselines spell out the old expressions directly, so they are not
redirected by the `csimp` rules for `mainVar` and `mainDegree`.

The 50 fixtures vary the number of variables (2/8/32/128), term count
(128/2048/8192), main-variable position, and lex/grevlex ordering. Additional
cases put the main variable in just the first or last lexicographic term;
zero and constant polynomials include the zero-variable case. These synthetic
inputs compare query implementations, not whole characteristic-set algorithms.

Before timing, all variants are checked against a separate reference over raw
exponent vectors, including a larger set of small fixtures and reversed insertion
orders. This is executable validation, not a proof of equivalence.
Each variant calibrates a warm batch to at least 20 ms, then runs seven trials
with variant order rotated. Native timings include a scalar hash, the existing
lean-bench opaque consumer, and loop overhead; input construction, validation,
calibration and JSON output are excluded. The JSON retains raw batch timings,
repeat counts and per-call median/min/max. In very small cases the consumer and
loop overhead can be a substantial part of the result.

### Experimental Initial.lean variants

```bash
LEAN_NUM_THREADS=2 ./bench/run.sh initial-variants bench/.lake/initial-variants.json
LEAN_NUM_THREADS=2 ./bench/run.sh initial-variants --verify
```

[InitialVariants.lean](CharacteristicSetBench/InitialVariants.lean) compares both
`initialOf` and `initial` using standard baselines, the production Internal
implementations, and two experimental candidates:

- `original`: frozen list/filter/map/lookup definitions. The `initial` baseline
  uses the current optimized `mainVar`, isolating this round of changes.
- `initial.standard`: also freezes the nested `mainVar` expression, for a complete
  standard-definition baseline.
- `two-pass`: production calls compiled through `initialOf_eq_internal` and
  `initial_eq_internal`; determine the degree, then build the retained terms directly,
  and check zero using the cached term count.
- `distinct`: an experimental two-pass fold inserting retained keys directly.
  It relies on fixed-degree erasure being injective, constructs `MvPoly` through
  its internal map field, and retains `0 + c` from the original constructor.
  It has no formal extraction-equivalence proof and is used only by this benchmark.
- `single-pass`: an experimental fold that resets its output whenever a higher
  degree appears. This candidate has no formal equivalence proof and is used only
  by this benchmark.

The 46 fixtures cover 2/8/32 variables, 128/2048 terms, lex/grevlex order,
one/half/all retained terms, and rising/falling degrees that exercise discarded
partial outputs. Zero and constant cases include zero variables. Independent
raw-term references check every variant before timing; additional verification
checks every selected coordinate in smaller fixtures, including degree zero and
non-main variables.

Seven trials rotate variant order, with separate warm-up/calibration targeting
20 ms batches for each variant. Timings include a full output hash and opaque
consumer, exclude preparation and checks, and describe repeated warm inputs.
JSON records raw batch timings, call counts, per-call samples, output term counts,
and median/min/max. Full output consumption can dilute an extraction speedup,
especially when every input term is retained; this is not a pure tree-building
timer or a whole characteristic-set benchmark.

### Registered microbenchmarks

Run from the repository root; the script builds the native executable first:

```bash
./bench/run.sh list
./bench/run.sh verify
./bench/run.sh run --tag basic --export-file basic.json
./bench/run.sh run --tag triangular --export-file triangular.json
./bench/run.sh run --tag reduced --export-file reduced.json
./bench/run.sh run --tag pseudo --export-file pseudo.json
./bench/run.sh run --tag main --export-file before.json
./bench/run.sh run --tag main --baseline before.json --export-file after.json
```

`list` shows the available benchmarks; use `--tag main,supplement` to include the supplementary cases. Each configuration is sampled three times, and JSON exports retain the samples for later comparison. In the results, `param` counts input terms per polynomial for the query, reduction, prefix replacement and basic-set benchmarks; for `pseudo`, it is the dividend degree (`successive`) or half that degree (`degreeJump`), while `constant` counts rational dividend terms and `sequence` is the degree d in x*y^d+d. `per-call` is the time per operation, including full result hashing. The `pseudo` cases exercise successive elimination, degree jumps, rational division by 2, and right-to-left division by [x+1, y+1], with inputs prepared outside the timer. The `reduced` cases compare first and last failure in a prepared eight-divisor list, measuring distinct short-circuit paths rather than an optimization speedup. The verdict describes how the measured time scales with input size; it is a diagnostic, not a proof of complexity.
